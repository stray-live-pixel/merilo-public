# Choice: выбрать категорию для реальной задачи

Режим choice нужен, когда у тебя есть материал и несколько допустимых вариантов, а выбрать надо один: отдел для обращения, тип обратной связи или маршрут обработки документа.

**Результаты ниже иллюстративные.** Это сокращённые фрагменты JSON, а не проведённые здесь замеры. Значения модели могут отличаться.

## Направить обращение клиента в нужный отдел

### Задача пользователя

Ты получаешь обращения в общую очередь поддержки. Нужно определить, кто должен первым взять сообщение: специалисты по оплате, техническая поддержка или отдел возвратов. Если тема неясна, обращение должно остаться для ручного разбора.

Клиент написал: «После обновления приложение закрывается сразу после запуска. Переустановка не помогла. Оплата подписки прошла нормально».

### Запрос

```bash
args=(
  -api-key "$OPENROUTER_API_KEY"
  -type choice                   # Выбираем одну категорию из списка.
  -model deepseek/deepseek-v4.1-flash
  -effort xhigh
  -repeats 1
  -question 'Выбери отдел по основной проблеме клиента. Упоминание оплаты без проблемы не делает обращение платёжным. Если подходящего отдела нет или данных недостаточно, выбери ручной разбор.'
  -choices 'оплата,техническая поддержка,возврат,ручной разбор'  # Допустимые названия результата.
)

# -context явно задаёт само обращение, а не инструкцию классификатору.
merilo "${args[@]}" \
  -context 'После обновления приложение закрывается сразу после запуска. Переустановка не помогла. Оплата подписки прошла нормально.'
```

### Пример результата

```json
{
  "type": "choice",
  "choice": "техническая поддержка",
  "probabilities": {
    "оплата": 0.01,
    "техническая поддержка": 0.96,
    "возврат": 0.01,
    "ручной разбор": 0.02
  },
  "repeats": 1,
  "completed": 1,
  "attempt_count": 1
  ...
}
```

### Как использовать результат

Основная проблема — падение приложения, поэтому результат указывает на техническую поддержку. Слово «оплата» присутствует, но правило в question помогает отличить основную проблему от фоновой информации.

Твоя система может прочитать поле choice и назначить отдел. Сам CLI не создаёт тикет и никуда не отправляет обращение. Вероятность 0.96 — оценка модели, а не гарантия правильного назначения. Значение «ручной разбор» — обычная категория, которую мы явно предусмотрели для неопределённых случаев.

## Разобрать обратную связь перед планированием доработок

### Задача пользователя

Ты ведёшь продуктовый backlog и хочешь разделять сообщения на ошибки, пожелания и вопросы. Один и тот же отзыв можно трактовать по-разному, поэтому нужно получить пять оценок и выбрать категорию по медианным вероятностям.

Отзыв: «Вечером экран слишком яркий. Добавьте, пожалуйста, тёмную тему».

### Запрос

```bash
args=(
  -api-key "$OPENROUTER_API_KEY"
  -type choice                   # Результат — одна категория, не числовой балл.
  -model deepseek/deepseek-v4.1-flash
  -effort xhigh
  -repeats 5                     # Собираем пять успешных оценок.
  -concurrency 2
  -question 'Классифицируй обратную связь. Ошибка — существующая функция работает неправильно. Пожелание — просьба добавить или изменить возможность. Вопрос — запрос объяснения. Если ни один вариант не подходит, выбери другое.'
  -choices 'ошибка,пожелание,вопрос,другое'
)

merilo "${args[@]}" \
  -context 'Вечером экран слишком яркий. Добавьте, пожалуйста, тёмную тему.'
```

### Пример результата

```json
{
  "type": "choice",
  "aggregation": "median",
  "choice": "пожелание",
  "median_probabilities": {
    "ошибка": 0.1,
    "пожелание": 0.8,
    "вопрос": 0.04,
    "другое": 0.04
  },
  "repeats": 5,
  "completed": 5,
  "attempt_count": 5
  ...
}
```

### Как использовать результат

Отзыв можно включить в список пожеланий: клиент просит новую возможность, а не сообщает о поломке существующей. Значение 0.8 — медиана вероятности категории «пожелание» среди пяти ответов.

Как рассчитывается итог по нескольким оценкам, описано отдельно в [методике](methodology.md).

Если отдельные оценки расходятся, отзыв можно оставить на обсуждение продуктовой команде. Для этой задачи итоговая категория помогает пополнить backlog, а не автоматически обещать клиенту реализацию.

## Выбрать маршрут для письма, в котором несколько вопросов

### Задача пользователя

В компанию приходит письмо о возврате оплаты и юридическом основании отказа. Нужно не потерять одну из тем при автоматической маршрутизации. Поэтому ты заранее вводишь вариант «ручной разбор»: если одного отдела недостаточно, письмо должен прочитать координатор.

Для оценки используем письмо целиком, чтобы не потерять связь между просьбами клиента.

### Запрос

```bash
args=(
  -api-key "$OPENROUTER_API_KEY"
  -type choice                   # Ровно один маршрут обработки письма.
  -model deepseek/deepseek-v4.1-flash
  -effort xhigh
  -repeats 1                     # Для этого сценария достаточно одного вызова.
  -question 'Выбери маршрут письма: бухгалтерия для расчётов и платежей, юристы для правовых вопросов, поддержка для использования продукта. Если письмо требует участия нескольких отделов, выбери ручной разбор.'
  -choices 'бухгалтерия,юристы,поддержка,ручной разбор'
)

# Письмо клиента с двумя связанными вопросами.
merilo "${args[@]}" -context - <<'TEXT'
Здравствуйте!
Верните, пожалуйста, оплату по заказу 1842: услугу мы не получили.
Если возврат невозможен, укажите пункт договора и правовое основание отказа.
TEXT
```

### Пример результата

```json
{
  "type": "choice",
  "choice": "ручной разбор",
  "probabilities": {
    "бухгалтерия": 0.2,
    "юристы": 0.15,
    "поддержка": 0.05,
    "ручной разбор": 0.6
  },
  "repeats": 1,
  "completed": 1
  ...
}
```

### Как использовать результат

Это успешная классификация, а не ошибка CLI. Модель выбрала предусмотренный маршрут для письма с несколькими темами. Внешняя система может оставить его координатору, который назначит участников.

CLI не назначает автоматический порог уверенности и не принимает решение о возврате денег. Если тебе нужен дополнительный порог, применяй его во внешнем инструменте к probabilities или median_probabilities. Сценарий использования одного набора проверок для отчёта описан в [примерах конфигураций](configurations.md).


## Различать ошибку, пожелание и вопрос по правилам команды

### Задача пользователя

Команда разбирает обратную связь. Просьбу добавить новую возможность важно отличать от сообщения о поломке. Для этого каждому варианту даём определение, общее для всех отзывов.

Определения категорий можно передать прямо в запросе, без отдельного файла. В question описаны правила команды, а choices содержит короткие названия результата.

### Запрос

```bash
# Правила классификации записаны прямо в конфиге этого запроса.
merilo \
  -api-key "$OPENROUTER_API_KEY" \
  -config '
{
  "defaults": {
    "model": "deepseek/deepseek-v4.1-flash",
    "effort": "xhigh"
  },
  "checks": [
    {
      "id": "feedback",
      "type": "choice",
      "question": "Классифицируй отзыв. «Ошибка» — существующая функция работает неправильно. «Пожелание» — просьба добавить или изменить возможность. «Вопрос» — просьба объяснить работу продукта. «Другое» — ни один вариант не подходит.",
      "choices": ["Ошибка", "Пожелание", "Вопрос", "Другое"]
    }
  ]
}

' \
  -context 'Добавьте, пожалуйста, возможность выгружать отчёт в Excel.'
```

### Пример результата

```json
{
  "checks": [
    {
      "id": "feedback",
      "type": "choice",
      "choice": "Пожелание",
      "probabilities": {
        "Ошибка": 0.02,
        "Пожелание": 0.94,
        "Вопрос": 0.02,
        "Другое": 0.02
      },
      "status": "completed"
    }
  ]
  ...
}
```

### Как использовать результат

Отзыв можно направить в очередь предложений: автор просит новую возможность, а не описывает нарушение работы существующей. Определения в вопросе помогают последовательно применять правила команды к следующим сообщениям. Отдельного поля описания у варианта нет — смысл задаётся в `question`, а в результате остаётся короткая категория.

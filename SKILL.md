# Мерило (`merilo`)

Используй установленную команду `merilo` из PATH. Явный вызов скилла вместе с вопросом об оценке означает запрос результата от Merilo. Собственный разбор агента может дополнять результат, но не заменять запуск. Если нужны настройки или доступ, подготовь запуск и явно запроси недостающее; не выдавай собственное мнение за выполненную оценку. Просьбы изменить скилл, установить приложение или объяснить его работу сами по себе не запускают оценку.

Эта инструкция целиком встроена в бинарник: `merilo skill` печатает её текст. Обновление приложения обновляет установленный скилл.

## Запуск

Проверь доступность через `merilo version` и `merilo -h`. Для готового релиза Go и исходники не нужны. Если команда отсутствует, сообщи об этом; установка приложения — отдельное действие. Обновление по запросу пользователя: `merilo update` (в автоматизации `merilo update --yes`); нестандартный каталог скиллов задаётся `--codex-home`. После обновления перезагрузи скилл.

### Ручной подбор и готовые настройки

Для свободного вопроса прочитай [путь от запроса до внедрения](#от-свободного-вопроса-до-полезного-запуска). Проведи пользователя последовательно: понять нужный результат → согласовать подходящую модель/effort → предложить методику, полезные альтернативы и повторы → получить подтверждение конкретного запуска → выполнить Merilo → объяснить результат. После успешного примера предложи разобрать регулярное применение; при согласии помоги спроектировать и реализовать интеграцию.

Полный пользовательский конфиг с понятным контекстом или достаточно точные инструкции разрешают запуск без повторного согласования и обязательной экскурсии. Сохраняй явно заданные и ранее согласованные параметры, включая документированные значения по умолчанию. Обсуждай только существенные пробелы. Конфиг, который агент сам составил из свободного вопроса, не отменяет подтверждение. Молчание не является согласием.

Если материал задан ссылкой, сначала прочитай источник и подготовь содержательный контекст: Merilo ссылки не загружает. Сохраняй факты и ограничения источника, не подмешивай собственный желаемый вывод. Если материал недоступен, запроси его до оценки. После подтверждения выполни команду и проверь JSON. При ошибке сообщи, что оценка не получена, и конкретное препятствие; собственный ответ агента не закрывает запрос на оценку Merilo.

### Провайдер и авторизация

Если провайдер не задан, приоритет скилла — **Codex по подписке ChatGPT**, затем **OpenRouter**, если Codex недоступен. У CLI собственный дефолт остаётся `openrouter`, поэтому передавай `-provider codex` явно; в новом конфиге записывай `defaults.provider`.

- **Codex:** проверь наличие CLI и `codex login status`. Нужен вход через ChatGPT; вход по API-ключу не подходит для подписки. Не читай и не копируй токены. Оценки расходуют общие лимиты подписки Codex.
- **OpenRouter:** используй `-provider openrouter -api-key "$OPENROUTER_API_KEY"`. Утилита сама не читает окружение, `.env` или файл ключа. Проверяй наличие ключа без вывода его значения; не сохраняй его в проект или конфиг. Отправная модель для резерва — `deepseek/deepseek-v4.1-flash`; подбирай поддерживаемый effort по сложности задачи, а не автоматически `xhigh`. Это платный API; согласуй конкретную пару модель/effort до резервного запуска.
- Если Codex отсутствует, нет входа через ChatGPT, исчерпан лимит или провайдер недоступен, проверь готовность OpenRouter. При согласованном резервном варианте и наличии ключа выполни одну резервную серию через Merilo. Для свободного вопроса включай резервные настройки и факт оплаты API в исходное предложение; если резерв не был согласован, явно запроси подтверждение его настроек перед запуском. Если доступа нет к обоим провайдерам, сообщи, какой доступ нужен.
- Если резерв заранее не согласован, явный выбор Codex или заданный провайдер в пользовательском конфиге не разрешает автоматическую замену: предложи резерв и дождись согласия. При запрете платного API OpenRouter не запускай. Ошибка параметров, контекста или формата ответа сама по себе не означает недоступность провайдера. Не переключай провайдеры по кругу.
- Не смешивай результаты разных провайдеров в одну медиану. При резервном запуске сохрани критерий, контекст и число повторов; отдельно укажи ошибку и доступный расход первой серии. При смене провайдера выбирай подходящую ему модель и effort.

### Модели, effort и расход

Модель и effort обязательны. Для Codex проверь актуальный каталог `codex debug models --bundled`: выводи только идентификаторы, описания и поддерживаемые effort, без больших блоков внутренних инструкций. Наличие в каталоге не гарантирует доступ аккаунта. Не заменяй явно выбранную модель и не запускай платные пробы для подбора.

Выбирай модель по сложности материала, неоднозначности критерия и последствиям ошибки. Для простой категоризации начинай с экономной модели и низкого effort; неоднозначные критерии и сложный контекст могут оправдать более сильную модель. Высокая цена ошибки требует проверки на примерах с известным ответом, а не только дорогой модели. При согласовании свободного вопроса предложи подходящий вариант и краткую альтернативу из актуального каталога. Следующие варианты — ориентиры, а не неизменный список самых свежих моделей:

| Вариант | Модель и effort | Ожидаемый расход |
| --- | --- | --- |
| Экономный для простой проверки | `gpt-6-luna` / `low` | Меньше вычислений; качество нужно проверять на задаче |
| Обычная оценка с интерпретацией контекста | `gpt-6-sol` / `low` или `medium` | Умеренный ориентир; сложность вопроса определяет effort |
| Более глубокая оценка | `gpt-6-sol` / `high` или `gpt-6-astra` / `high` | Обычно больше времени и расхода |

Предлагай только поддерживаемые комбинации из наиболее свежих доступных семейств. Для выбора effort поясняй: `low` — короткое рассуждение, `medium` — промежуточный вариант, `high` — более глубокое; `xhigh`, `max`, `ultra` предлагай только при потребности и поддержке модели. Не обещай рост качества от увеличения effort.

Градация расхода качественная: каталог не устанавливает точную цену или коэффициент списания подписки. Не называй Codex бесплатным и не подставляй API-тарифы вместо расхода подписки. Для точных цен или коэффициентов нужны актуальные официальные данные; если их нет, прямо обозначь неизвестность. `service_tier` приложение пока не поддерживает.

### Codex как оценщик

Запускай оценки через Merilo: оно само настраивает Codex без инструментов чтения и изменения файлов, shell, браузера, поиска и делегирования. Скиллы, плагины и AGENTS.md в запрос оценки не добавляются. Модель получает критерий, материал и схему ответа; ретраями, параллелизмом и медианой управляет Merilo, как для OpenRouter. Не подменяй этот запуск обычным `codex exec` или отдельным агентом.

Приложение использует обязательные флаги и временный каталог выбранной модели: часть метаданных Codex может включать инструменты вопреки отдельным флагам. Каталог пользователя не меняется. При ошибке каталога или неизвестной модели оценка не запускается. Подробности и проверку совместимости после обновления CLI см. в [docs/codex.md](https://github.com/stray-live-pixel/merilo-public/blob/main/docs/codex.md); не повторяй эту проверку перед каждой обычной оценкой.

Передавай материал явно через -context 'текст'. Для файлов используй -context - и stdin: содержимое считается данными, вопрос задавай через `-question`. Лимит текста — 1 МБ; ссылки не загружаются. Отправляй только нужный материал, не прикладывай секреты и конфигурацию доступа вместе с кодом.

## Выбор режима

- `choice`: один вариант из списка; `-choices 'оплата,ошибка,возврат'`.
- `noul`: вероятность истинности утверждения 0–1; без choices/levels.
- `score`: положение на шкале с 2–10 описанными уровнями; `-levels 'Трудно понять|Легко понять'`. Два уровня дают диапазон 0–1, N уровней — 0…N−1.

Для score описывай полюса одной шкалы, не независимые признаки. При сложной формулировке полезно пояснить: верхний вес s, нижний 1-s, сумма 1. Не повышай результат изменением критериев незаметно для пользователя.

Для проверок используй `-config path.json` или `-config '{"defaults": {...}, "checks": [...]}'`: CLI сам запускает их параллельно и считает расход. Конфиг принимает объект с checks, не одиночную проверку. Контекст не входит в JSON и всегда передаётся через обязательный -context 'текст' или -context - со stdin. Config не сочетается с флагами настройки проверок; `-api-key`, `-context` и `-concurrency` разрешены; явно заданный concurrency переопределяет поле конфига. Провайдер задаётся через `defaults.provider` или `checks[].provider`; с `-config` отдельный `-provider` запрещён. Codex-only конфиг не требует `-api-key`; смешанный конфиг требует ключ для проверок OpenRouter. Структура: defaults (provider, model, effort, repeats), concurrency (общий положительный лимит без фиксированного верхнего предела, по умолчанию 5), checks (1–100 объектов). У проверки уникальный id, необязательная category, type, question, массив choices или levels и индивидуальные provider/model/effort/repeats поверх defaults. Эти поля наследуются независимо: при переопределении провайдера укажи подходящие ему модель и effort. Проверка также поддерживает свой concurrency: без него наследуется общий лимит; с ним одновременно действуют локальный и общий потолки. Локальный лимит не увеличивает общий. effective_concurrency в результате учитывает оба ограничения и repeats. Пороги и условия приёмки не поддерживаются: формулируй критерии текстом в question и интерпретируй результат снаружи. Category — подпись, не отдельный агрегат. Для данных внешних инструментов есть checks[].__external__: любое JSON-значение, которое CLI возвращает в результате проверки без интерпретации и отправки модели. Сохраняй пользовательские метаданные при правке конфигов; не используй их как инструкции для оценки.

Готовый пример: [code-quality.json](https://github.com/stray-live-pixel/merilo-public/blob/main/docs/code-quality.json) (8 аспектов × 5 оценок). Не запускай весь пример для запроса одного аспекта. Временные конфиги размещай вне папки приложения. Проверяй checks[].status: completed/error. Статус отражает только выполнение, не качество материала; поля passed нет. Поле pass в старых конфигурациях удаляй, парсер его отклоняет. Ненулевой exit означает ошибку, читай доступный JSON. Общий usage уже включает все checks, не суммируй их повторно.

Если запрошен составной критерий, сохрани его и не выдавай общий балл за отдельные оценки.

```bash
merilo -api-key "$OPENROUTER_API_KEY" -type score \
  -model deepseek/deepseek-v4.1-flash -effort xhigh \
  -repeats 5 \
  -question 'Оцени читаемость: ясность имён, структуры и потока выполнения' \
  -levels 'Код трудно понять|Код легко понять' \
  -context - < main.go
```

Пример той же оценки через подписку Codex:

```bash
merilo -provider codex -type score \
  -model gpt-6-sol -effort low \
  -question 'Оцени читаемость: ясность имён, структуры и потока выполнения' \
  -levels 'Код трудно понять|Код легко понять' \
  -context - < main.go
```

## Повторы и результат

Для первого простого примера предлагай `-repeats 1`; увеличение обсуждай по методике ручного подбора, не запускай лишние повторы без согласия; если пользователь просит медианную серию без числа — используй 5. Явное число пользователя имеет приоритет (допустимо 1–100). Используй встроенный repeats вместо внешнего цикла: CLI сохраняет расход попыток; параллелизм задаётся -concurrency, по умолчанию 5. Явный запрос на 100 параллельных оценок выполняй с -repeats 100 -concurrency 100, не разбивай его вручную.

Для noul/score итоговое одноимённое поле — медиана при repeats > 1. Для choice выбирается максимум `median_probabilities`; эти числа не обязаны суммироваться в 1, при равенстве выбирается первый вариант. Исходные результаты доступны в `samples[].result`.

Некорректный ответ CLI повторяет до трёх раз после первой попытки, добавляя только тип последней ошибки валидатора, без фактических значений в системную инструкцию. Контекст задачи не меняется; независимые повторы не разделяют историю ошибок. Не оборачивай это в бесконечные внешние повторы. Сеть и HTTP/API-ошибки автоматически не повторяются; сбои Codex CLI, авторизации, лимитов и таймаут также не запускают автоматический повтор. При неполной серии код завершения ненулевой, JSON содержит статистику и error, итоговой медианы нет. Не называй медианой всей серии значение по оставшимся ответам.

В отчёте указывай итог, число успешных оценок, разброс или значения серии, провайдер, модель/effort, стоимость и токены. Бери общий расход из верхнего `usage`, не суммируй его повторно с samples. При `usage_complete: false` обозначай расход как неполный, а не нулевой. Отличай количество оценок от `attempt_count` — числа фактических попыток.

Для Codex возвращается `billing: "chatgpt_subscription"`; `usage.cost` отсутствует, `usage_complete` равно `false`. Укажи доступные токены и использование подписки; денежную стоимость обозначай как недоступную, не как ноль. В смешанном конфиге денежная сумма отражает только известную часть расхода OpenRouter.

Медиана — устойчивый ориентир для сравнения при фиксированных условиях, а не доказательство качества или авторства. Для сравнения фиксируй провайдера, модель, effort, вопрос, уровни и повторы; медиана снижает влияние крайних ответов, но не исправляет систематическую ошибку. Вероятности модели не калиброваны; разброс серии не является доверительным интервалом. CLI не возвращает объяснений: не приписывай ему найденные дефекты. Изменение вопроса означает другую проверку, а не улучшение неизменного материала.

После реального успешного прогона предложи коротко разобрать, как применять проверку регулярно, если пользователь ещё не отказался и это не автоматический запуск. Продолжай интеграцию только при согласии, по [руководству](#после-результата-регулярный-процесс).

Не сохраняй разовые отчёты и экспериментальные скрипты в папку приложения. Если нужен файл результата, используй рабочую папку задачи или временный каталог и дай ссылку.

## Локальный интерфейс

По просьбе поэкспериментировать в браузере запусти `merilo -ui` (порт 8080, меняется -port), открой напечатанный адрес. Формы доступны без ключа; провайдер выбирается в технических настройках, а в конфигурации может переопределяться для каждой проверки. После смены провайдера укажи подходящую модель.

Для Codex используется вход CLI через ChatGPT. Ключ OpenRouter запрашивается только при запуске конфигурации с проверками OpenRouter либо передаётся через `-api-key` при запуске UI. Модалку можно закрыть; смена ключа сохраняет формы и результаты. Экспорт команды включает шаблон `$OPENROUTER_API_KEY` только если он нужен; реальный ключ в экспорт не попадает.

В правой колонке — запуск, результат и экспорт JSON/команды. Тема автоматически следует системе. Вкладки Choice/Noul/Score/Конфигурация сохраняют отдельные черновики в памяти страницы; технические настройки отделены от задач. Шаблоны берутся из docs/ui-templates.json и готовых конфигов. Подробнее — [docs/ui.md](https://github.com/stray-live-pixel/merilo-public/blob/main/docs/ui.md). Запуск UI не разрешает самостоятельно выполнять все шаблоны с расходом API или подписки.

## От свободного вопроса до полезного запуска

Используй этот путь при ручном обращении без готовых настроек. Это короткий диалог вокруг задачи пользователя, не обязательная лекция обо всех функциях. Готовый пользовательский конфиг и уже согласованные решения не требуют повторного прохождения шагов.

### 1. Понять задачу и согласовать модель

Определи, какое решение пользователь хочет принять по результату: выбрать категорию, проверить утверждение, измерить свойство или получить несколько отдельных сигналов. Используй доступный контекст; спрашивай только то, без чего изменится смысл оценки. Не начинай с опросника о будущем внедрении.

Мягко уточни исходную формулировку, сохранив цель. Например, «категоризируй обращение» можно предложить как «выбери отдел по основной просьбе клиента». Если меняется критерий, появляются категории, правило при нескольких темах или допущение, покажи это пользователю. Не придумывай правила его организации и не подменяй широкий вопрос удобным узким показателем без согласия.

Предложи конкретные провайдер, модель и effort, объяснив выбор через задачу:

- Ясные короткие тексты, простые категории, явные признаки: экономная модель и низкий effort.
- Неоднозначные обращения, несколько условий, оценка качества по описанным уровням: сбалансированная модель, низкий или средний effort.
- Сложные противоречия, длинный контекст, тонкие критерии: более сильная модель или больший effort с объяснением ожидаемой пользы. Это гипотеза о подходящей конфигурации, не доказанная точность.

Опирайся на актуальные доступные модели и поддерживаемые effort из основного скилла. Дай одну-две разумные альтернативы с качественным сравнением расхода и времени. Не предлагай дорогую модель как обязательную страховку. Если категории определяются точным правилом, честно скажи, что обычный фильтр может оказаться проще; запрошенную оценку через Merilo всё равно подготовь.

Согласуй модель до подробного выбора методики: «Для этой простой категоризации предлагаю …; альтернатива … нужна, если … . Какой вариант выбираем?» При уже заданной модели сразу переходи к методике. Резервный OpenRouter, если предлагается, согласуй вместе с его моделью/effort и платным характером API.

### 2. Согласовать методику и повторы

После выбора модели предложи рекомендуемый вариант и **всегда хотя бы одну осмысленную альтернативу**. Поясняй пользу на материале пользователя: какой результат он получит, какое решение сможет принять, что останется неизвестным и какие дополнительные ресурсы нужны. Не перечисляй режимы без связи с кейсом.

Покажи вклад самого Merilo: согласованные категории или шкала задают единый формат оценки, JSON позволяет использовать результат в процессе, сохранённые настройки — повторять проверку, а серия — видеть устойчивость суждений модели. Выбери только полезное в этом кейсе. Не приписывай приложению повышение точности само по себе: смысловую оценку делает выбранная LLM.

| Нужный результат | Методика и конкретная польза | Полезная альтернатива и её границы |
| --- | --- | --- |
| Один отдел для обращения | `choice`: одна категория из согласованного списка для маршрутизации | Несколько `noul` в конфиге, если важны независимые признаки: возврат, ошибка, угроза ухода. Признаки не выбирают один отдел автоматически |
| Проверить, просит ли клиент возврат | `noul`: числовая оценка конкретного утверждения по тексту | `choice`, если нужен один явный ярлык, например «просит / не просит / недостаточно данных» |
| Оценить срочность или понятность ответа | `score`: положение на одной шкале с понятными уровнями для сравнения примеров | `choice`, если процессу нужны только фиксированные ярлыки, без промежуточного балла |
| Получить отдел, срочность и признаки | Конфиг с отдельными проверками: разные сигналы из одного контекста | Одна проверка самого важного признака для более дешёвого первого примера |

Не принуждай к неподходящему режиму ради альтернативы: можно предложить другой состав проверок или число повторов в том же режиме. Если обсуждаешь менее подходящий режим, явно объясни, на какой другой вопрос он отвечает. Конфиг — способ объединить проверки, а не четвёртая шкала и не автоматическое усреднение разных критериев.

Для `choice` согласуй список и правило выбора при нескольких подходящих категориях; при необходимости предложи категорию «другое / недостаточно данных». Для `noul` сформулируй проверяемое утверждение и границы доступных сведений: оценка не заменяет проверку фактов. Для `score` опиши полюса одной шкалы через наблюдаемые свойства и уточни, что означает высокий балл.

Отдельно объясни варианты числа вызовов:

- **Один вызов** — разумный первый пример для ясного вопроса: меньше расхода, но устойчивость ответа неизвестна.
- **Серия, обычно 3–5 повторов** — полезна при неоднозначности или сравнении версий: показывает разброс и даёт медиану. Если пользователь просит медианную серию без числа, используй 5. Повторы требуют дополнительных запросов; параллелизм может уменьшить ожидание, но не число оплачиваемых вызовов.
- **Разные проверки** — отвечают на разные вопросы, например тема и срочность; их нельзя выдавать за повторы одного критерия. Оценки разных моделей тоже не объединяй в общую медиану.

Поясни агрегацию выбранного режима: для `score`/`noul` медиана чисел снижает влияние крайних ответов; для `choice` Merilo выбирает максимум медианных вероятностей категорий, а не большинство голосов. Повторение одной модели не устраняет её систематические ошибки. Стабильность не доказывает правильность; число 0,9 не гарантирует 90% точности. При одном вызове медианы серии нет.

Сведи предложение к конкретному запуску: материал, уточнённый вопрос, режим, категории/уровни, согласованная модель/effort, повторы и при необходимости параллелизм. Укажи число проверок × повторы; дополнительные попытки из-за некорректного ответа тоже могут увеличить расход. Предлагаемые варианты запускай только в выбранном пользователем объёме, а не все для демонстрации. Закончи явным «Запустить этот вариант?»; после подтверждения не вводи ещё одно согласование тех же настроек.

### 3. Выполнить и помочь понять результат

Запусти Merilo по основному скиллу, проверь завершённость и фактический JSON. Покажи ответ на исходный вопрос, успешные оценки, значения/разброс серии и расход. Объясни, как применить результат именно в этом примере и чего он не устанавливает. Собственную интерпретацию отделяй от результата CLI, который не возвращает объяснений.

Если сравнение нескольких вариантов было согласовано, покажи различия результата, времени (если измерено) и расхода. Не объявляй победителя по одному удачному примеру и не выбирай высокий балл как доказательство лучшей модели. После слабого результата предложи конкретное изменение критерия или проверку на примерах с известным ответом; не увеличивай серию автоматически.

### После результата: регулярный процесс

После успешного ручного прогона предложи один естественный следующий шаг с привязкой к кейсу: «Если такие обращения приходят регулярно, можем разобрать поток и настроить категоризацию через CLI: фиксированные категории, обработку спорных случаев и проверку качества. Разберём?» Не начинай внедрение без согласия, не повторяй предложение после отказа и не добавляй его в каждый автоматический отчёт.

При согласии помоги довести интеграцию до конкретного результата, а не только описать возможность:

1. Выясни нужные детали по ходу работы: источник текста, получатель результата, объём и частота, категории и цена ошибок, допустимые задержки/расход, спорные случаи и эталонные примеры. Не запрашивай всё сразу, если часть уже ясна.
2. Предложи минимальную схему: источник → подготовка контекста → Merilo с версионируемым конфигом → проверка exit code и статусов JSON → обработчик результата → целевая система или человек. Укажи, где нужны данные и доступ пользователя.
3. Подготовь в проекте интеграции конфиг и воспроизводимую CLI-команду без секретов; при необходимости реализуй адаптер, обработку ошибок и журнал настроек/результатов/расхода. В Merilo один контекст на запуск: поток разных обращений обрабатывает внешний адаптер. Учитывай общий параллелизм процессов и проверок. Не приписывай CLI встроенный планировщик, приёмку по порогам или автоматическую маршрутизацию.
4. Проверь на согласованной небольшой выборке с человеческой разметкой, включая неоднозначные случаи. Для категоризации оцени ошибки по категориям и случаи передачи человеку; для шкалы — согласие с экспертными оценками. Пороги и правила обработки живут снаружи Merilo и проверяются на данных. Не обещай производственную точность по первому примеру.
5. Помоги подключить запуск к выбранному пользователем процессу в пределах полученного разрешения, проверь результат и объясни, как повторить запуск и менять настройки. Согласие обсуждать внедрение разрешает подготовку решения, но не самостоятельное включение расписания или изменение маршрутизации реальных обращений. Если доступ блокирует подключение, передай готовые артефакты и точно назови оставшееся действие.

Повторяющийся процесс использует закреплённые настройки без интерактивного выбора модели при каждом обращении. Смена модели, критериев или бюджета — отдельное осознанное изменение конфигурации, а не скрытая оптимизация агента.
